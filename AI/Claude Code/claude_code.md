# Claude Code란?

- 터미널·IDE·브라우저에서 동작하는 `에이전틱 코딩 도구`
- 코드베이스를 읽고, 파일을 수정하고, 명령을 실행하고, 개발 도구와 연동됨
- 챗봇과 결정적으로 다른 점

| | 챗봇 | Claude Code |
| --- | --- | --- |
| 역할 | 질문에 답하고 기다림 | 스스로 탐색·계획·구현 |
| 코드 | 내가 쓰고 리뷰를 요청 | 원하는 것을 설명하면 알아서 구현 |
| 범위 | 대화창 안 | 파일시스템, 셸, 외부 도구 |

- 즉 `무엇을 만들지 설명하면 어떻게 만들지는 도구가 찾아내는` 방식
  - 그만큼 자율성이 크고, 그 자율성을 다루는 법을 익히는 데 학습 곡선이 있음

<br>

## 실행 환경

같은 엔진이 여러 표면(surface)에서 돌아간다.

| 표면 | 특징 |
| --- | --- |
| 터미널 | 가장 기능이 완전한 CLI |
| VS Code / Cursor | 인라인 diff, `@` 멘션, 플랜 리뷰 |
| JetBrains | IntelliJ·PyCharm 등 플러그인 |
| 데스크톱 앱 | diff 시각적 검토, 여러 세션 병렬, 예약 작업 |
| 웹 / 모바일 | 로컬 설치 없이 실행, 긴 작업을 걸어두고 나중에 확인 |

- 중요한 점: `표면이 달라도 같은 설정을 공유함`
  - 저장소의 `CLAUDE.md`, 설정 파일, MCP 서버가 모든 표면에서 그대로 동작
- 세션을 표면 간에 `이동`시킬 수도 있음
  - 터미널에서 시작 → 데스크톱에서 diff 검토 → 외출 중 모바일에서 이어가기

### 설치

```bash
# macOS, Linux, WSL
curl -fsSL https://claude.ai/install.sh | bash

# Homebrew
brew install --cask claude-code
```

```bash
cd your-project
claude
```

## 무엇을 할 수 있나

- `미뤄둔 반복 작업` 자동화
  - 테스트 없는 코드에 테스트 작성, 린트 에러 일괄 수정, 의존성 업데이트, 릴리스 노트 작성
- `기능 구현과 버그 수정`
  - 에러 메시지를 붙이면 코드베이스를 추적해 근본 원인을 찾아 수정
- `git 연동`
  - 스테이징, 커밋 메시지 작성, 브랜치 생성, PR 생성
- `파이프라인에 끼워넣기` — Unix 철학에 맞게 조합 가능

```bash
# 로그를 파이프로 넘겨 분석
tail -200 app.log | claude -p "이상 징후가 있으면 알려줘"

# 변경된 파일만 보안 관점에서 리뷰
git diff main --name-only | claude -p "이 파일들을 보안 관점에서 검토해줘"
```

- `CI/CD에서 실행` — GitHub Actions, GitLab CI로 리뷰·트리아지 자동화
- `예약 실행` — 아침 PR 리뷰, 야간 CI 실패 분석 같은 반복 작업

## 확장 메커니즘

Claude Code의 실질적인 가치는 `확장 수단의 폭`에 있다.

| 수단 | 성격 | 쓰는 경우 |
| --- | --- | --- |
| `CLAUDE.md` | 상시 컨텍스트 | 모든 세션에 필요한 프로젝트 규칙 |
| `.claude/rules/` | 경로별 컨텍스트 | 특정 디렉토리·파일 타입에만 필요한 규칙 |
| 스킬 | 온디맨드 지식·워크플로우 | 때때로 필요한 절차. 호출할 때만 로드 |
| 슬래시 커맨드 | 명령 등록 | 자주 쓰는 프롬프트 |
| 서브에이전트 | 격리된 컨텍스트 | 탐색·리뷰처럼 파일을 많이 읽는 작업 |
| 훅(Hooks) | `결정론적` 실행 | 반드시 매번 실행돼야 하는 것 |
| MCP | 외부 연동 | DB, 이슈 트래커, 디자인 도구 |
| 플러그인 | 묶음 배포 | 위 요소들을 패키징해 설치 |
| Agent SDK | 라이브러리 | Claude Code의 하네스로 커스텀 에이전트 제작 |

### 훅이 특별한 이유

- `CLAUDE.md`의 지시는 `권고`임 — 모델이 읽고 따르려 하지만 보장되지 않음
- `훅`은 셸 명령으로 특정 시점에 실행되므로 `모델의 판단과 무관하게 강제됨`
  - "파일 수정 후 항상 포맷", "커밋 전 린트", "마이그레이션 폴더 쓰기 금지"
- 반드시 매번 일어나야 하는 일은 지시가 아니라 `훅`으로 써야 함

## 모델 선택

Claude Code는 여러 모델을 쓸 수 있고, `무엇을 고르는지가 결과와 비용을 크게 바꾼다`.

> ⚠️ 모델 라인업은 자주 바뀝니다. 아래는 체급별 성격이고, 현재 쓸 수 있는 모델과 기본값은 세션에서 `/model`로 확인하세요.

### 체급별 성격과 적합한 업무

| 체급 | 추론 | 속도 | 비용 | 적합한 업무 |
| --- | --- | --- | --- | --- |
| `Fable` | 최상 | 느림 | 높음 | 근본 원인 추적, 장애 디버깅, 아키텍처 결정, 보안 감사, 장시간 자율 작업 |
| `Opus` | 상 | 중간 | 중간 | 복잡한 로직, 버그 수정, 엣지 케이스, 중요한 설계 결정 |
| `Sonnet` | 중 | 빠름 | 낮음 | 기능 구현, 테스트 작성, 일상적인 코딩, 빠른 피드백 루프 |
| `Haiku` | 하 | 매우 빠름 | 매우 낮음 | 간단한 질의응답, 단순 변환, 배치 처리, 비용 최소화 |

### 각 체급의 장단점

- `Fable` — 가장 강력하지만 `가장 느리고 비쌈`
  - 장점: 모호한 문제에 강함. 스스로 검증을 잘 하므로 검증 리마인더가 덜 필요함
  - 단점: 한 턴이 수 분까지 걸릴 수 있어 대화형 반복에는 부적합
  - 쓰는 법이 다름: `단계를 지시하지 말고 원하는 결과를 설명`하는 편이 좋음. 작업을 잘게 쪼개지 말고 통째로 주는 것이 유리
  - 프롬프트도 다시 봐야 함 — 구형 모델용으로 쓴 `지나치게 처방적인 지시`가 오히려 품질을 떨어뜨림
- `Opus` — 능력과 속도의 균형점
  - 장점: 복잡한 추론이 필요한 대부분의 작업을 감당하면서 대화형으로 쓸 만한 속도
  - 단점: Sonnet보다 느리고 비쌈. 간단한 작업에는 과함
- `Sonnet` — 실무 기본값으로 가장 많이 쓰이는 체급
  - 장점: 빠른 반복이 가능하고 비용이 낮음. 기능 구현 품질이 충분함
  - 단점: 까다로운 버그나 아키텍처 판단에서는 상위 체급에 밀림
- `Haiku` — 속도와 비용이 전부인 경우
  - 장점: 초 단위 응답. 대량 처리에 적합
  - 단점: 다단계 추론이 필요한 작업에는 부적합

### 별칭으로 고르기

```bash
/model                  # 대화형 선택기
/model opus             # 체급 별칭
/model claude-opus-5-5  # 정확한 모델 ID
```

| 별칭 | 의미 |
| --- | --- |
| `best` | 쓸 수 있는 가장 강한 모델 |
| `fable` / `opus` / `sonnet` / `haiku` | 해당 체급의 최신 모델 |
| `opus[1m]` / `sonnet[1m]` | 1M 토큰 컨텍스트 윈도우로 실행 |
| `opusplan` | `계획은 Opus, 구현은 Sonnet` |
| `default` | 계정 기본값 |

- 시작할 때 지정: `claude --model sonnet`
- 설정 파일에 고정: `settings.json`의 `model`
  - 프로젝트 단위로 고정하려면 `.claude/settings.json`에 둠

### effort — 같은 모델에서 사고 깊이 조절

- 모델을 바꾸지 않고 `추론에 쓰는 토큰량`을 조절하는 축
- `low` → `medium` → `high` → `xhigh` → `max`

```bash
/effort          # 슬라이더
/effort high     # 직접 지정
```

| 레벨 | 쓰는 때 |
| --- | --- |
| `low` | 브레인스토밍, 초안, 빠른 답변 |
| `medium` | 일상적인 작업 |
| `high` | 버그 수정, 엣지 케이스 검토 |
| `xhigh` | 복잡한 아키텍처, 깊은 추론 |
| `max` | 보안 취약점 탐색처럼 비용보다 정확성이 중요한 작업 |

- 모델별 기본 effort가 다르므로 `/model`에서 확인하고 저장할 수 있음
- 한 번만 깊게 생각시키려면 프롬프트에 `ultrathink`를 넣으면 됨 — 세션 설정은 그대로 유지됨
- `체급을 올리는 것과 effort를 올리는 것은 다른 선택임`
  - 비용이 걱정이면 상위 체급으로 올리기 전에 `현재 체급의 effort를 올려보는` 편이 합리적인 경우가 많음

### 조합 전략

- `opusplan` — 계획 단계만 강한 모델에 맡기고 구현은 빠른 모델로
  - 설계 판단이 중요하지만 구현량이 많은 작업에 효율적
- `1M 컨텍스트` — 큰 코드베이스를 한 번에 다룰 때
  - 단, 넣을 수 있다고 다 넣으면 품질이 떨어짐 (바로 아래 절 참고)
- `폴백 체인` — 상위 모델이 사용량 한도나 거절로 막혔을 때 자동으로 하위 모델로 내려가게 설정 가능

### 선택 가이드

| 상황 | 모델 | effort |
| --- | --- | --- |
| 무엇을 쓸지 모르겠음 | `sonnet` | `medium` |
| 일상적인 기능 구현 | `sonnet` | `medium` ~ `high` |
| 재현이 어려운 버그 | `opus` | `high` ~ `xhigh` |
| 아키텍처·설계 결정 | `opus` | `xhigh` |
| 근본 원인 분석, 장시간 자율 작업 | `fable` | `high` ~ `xhigh` |
| 보안·성능 감사 | `fable` | `max` |
| 대규모 코드베이스 분석 | `opus[1m]` | `high` |
| 비용 최소화, 단순 작업 | `haiku` | `low` |

## 핵심 제약 — 컨텍스트 윈도우

> 대부분의 베스트 프랙티스는 `하나의 제약`에서 나온다. 컨텍스트 윈도우는 빠르게 차고, 차오를수록 성능이 떨어진다.

- 컨텍스트에는 대화 전체가 들어감 — 모든 메시지, 읽은 모든 파일, 모든 명령 출력
  - 디버깅 세션 하나나 코드베이스 탐색 한 번으로 수만 토큰이 소모될 수 있음
- 차오르면 앞선 지시를 "잊거나" 실수가 늘어남
- 관련: [토큰과 컨텍스트 윈도우](https://github.com/lcomment/development-recipes/blob/main/AI/LLM/토큰과_컨텍스트_윈도우.md)

### 컨텍스트 관리 수단

| 수단 | 용도 |
| --- | --- |
| `/clear` | 관련 없는 작업 사이에 컨텍스트 초기화 |
| `/compact` | 대화를 요약해 압축 (`/compact <지시>`로 보존 대상 지정) |
| 서브에이전트 | 탐색을 별도 컨텍스트에 격리하고 요약만 받음 |
| `/rewind` | 이전 체크포인트로 대화·코드 복원 |

## 권장 작업 흐름

### 검증 수단을 주는 것이 가장 중요하다

- Claude는 `작업이 끝나 보일 때` 멈춤
  - 실행할 검사가 없으면 "끝나 보인다"가 유일한 신호가 되고, `사람이 검증 루프가 됨`
- 모델이 읽을 수 있는 `pass/fail 신호`를 주면 루프가 스스로 닫힘
  - 테스트 스위트, 빌드 종료 코드, 린터, 스크린샷 비교

| 약한 요청 | 강한 요청 |
| --- | --- |
| 이메일 검증 함수를 만들어줘 | 이메일 검증 함수를 만들어라. 테스트 케이스는 ... 구현 후 테스트를 실행해라 |
| 빌드가 깨졌어 | 빌드가 이 에러로 실패한다: [에러]. 근본 원인을 고치고 빌드 성공을 확인해라 |

- 성공했다고 주장하는 대신 `증거를 보여주게` 하는 편이 좋음 — 테스트 출력, 실행한 명령과 결과

### 탐색 → 계획 → 구현 → 커밋

1. `탐색` — 플랜 모드(`Shift+Tab`)로 진입. 파일을 읽고 질문에 답하지만 수정하지 않음
2. `계획` — 구현 계획을 작성하게 함. 에디터로 열어 직접 수정 가능
3. `구현` — 플랜 모드를 벗어나 계획대로 구현. 테스트까지 실행
4. `커밋` — 커밋 메시지 작성과 PR 생성

- 단, `플랜 모드는 오버헤드`이기도 함
  - 오타 수정, 로그 한 줄 추가처럼 `diff를 한 문장으로 설명할 수 있으면` 계획을 건너뛰는 게 맞음
  - 계획이 유용한 경우: 접근 방식이 불확실할 때, 여러 파일을 바꿀 때, 낯선 코드를 다룰 때

### 큰 기능은 먼저 인터뷰시킨다

- 최소한의 설명만 주고 `모델이 거꾸로 질문하게` 함
  - 기술 구현, UI/UX, 엣지 케이스, 트레이드오프를 짚어줌
  - 충분히 다뤘으면 `SPEC.md`로 정리시키고, `새 세션`에서 그 스펙으로 구현
- 스펙을 정밀하게 만드는 데 쓴 시간이 구현을 지켜보는 시간보다 더 값어치가 큼

## 흔한 실패 패턴

| 패턴 | 증상 | 해결 |
| --- | --- | --- |
| `잡동사니 세션` | 한 작업 하다 딴 걸 묻고 다시 돌아옴 | 작업 사이에 `/clear` |
| `반복 교정` | 고쳐도 틀리고 또 고침 | 두 번 실패하면 `/clear` 후 더 구체적인 프롬프트로 재시작 |
| `과도한 CLAUDE.md` | 지시의 절반이 무시됨 | 가차없이 덜어내기 |
| `믿고 검증 안 함` | 그럴듯한데 엣지 케이스가 깨짐 | 검증 수단을 항상 제공 |
| `무한 탐색` | 범위 없이 "조사해줘" | 범위를 좁히거나 서브에이전트로 격리 |

- 특히 `반복 교정`은 컨텍스트가 실패한 접근들로 오염되는 상태임
  - 같은 문제로 두 번 이상 교정했다면, 깨끗한 세션에서 배운 것을 담아 다시 시작하는 게 거의 항상 빠름

<br>

## 비대화형 실행

```bash
# 단발 질의
claude -p "이 프로젝트가 무엇을 하는지 설명해줘"

# 스크립트용 구조화 출력
claude -p "모든 API 엔드포인트를 나열해줘" --output-format json
```

- CI 파이프라인, pre-commit 훅, 각종 스크립트에 끼워넣는 방식
- 대량 작업은 루프로 분산시킬 수 있음
  - 사전 승인 도구(`--allowedTools`)와 권한 모드를 함께 지정해 무인 실행
