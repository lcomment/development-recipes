# 권한과 설정 (settings.json)

- Claude Code가 `무엇을 할 수 있고 무엇을 할 수 없는지`를 정하는 체계
- 가장 중요한 전제부터

> **권한 규칙은 Claude Code가 강제한다. 모델이 강제하는 것이 아니다.**
> 프롬프트나 `CLAUDE.md`의 지시는 Claude가 `무엇을 시도할지`를 바꾸지만, Claude Code가 `무엇을 허용할지`는 바꾸지 않는다. 실제로 막으려면 권한 규칙, 권한 모드, 또는 훅을 써야 한다.

- 따라서 `"위험한 명령은 실행하지 마"` 같은 지시는 방어가 아님
  - 프롬프트 인젝션이나 모델의 판단 착오로 우회됨
  - 권한 설정이 유일하게 믿을 수 있는 층

<br>

## 통제의 세 층

| 층 | 결정하는 것 | 수단 |
| --- | --- | --- |
| `권한 모드` | 물어볼지 말지의 기본값 | Manual, auto, plan 등 |
| `권한 규칙` | 특정 도구·명령을 허용/확인/차단 | `allow`, `ask`, `deny` |
| `샌드박스·훅` | 실행된 동작이 도달할 수 있는 범위 | OS 격리, `PreToolUse` 훅 |

- 모드가 `기준선`을 정하고, 규칙이 그 위에 `예외`를 얹는 구조
- 반드시 매번 특정 검사를 돌려야 한다면 규칙이 아니라 `훅`

<br>

## 설정 파일 위치와 우선순위

높은 쪽이 낮은 쪽을 덮어쓴다.

| 순위 | 파일 | 범위 |
| --- | --- | --- |
| 1 | 관리형 설정 (MDM, 콘솔) | 조직 전체 — 아무것도 덮어쓸 수 없음 |
| 2 | `claude --settings` | 이번 세션 |
| 3 | `.claude/settings.local.json` | 나, 이 프로젝트 (gitignore 대상) |
| 4 | `.claude/settings.json` | 프로젝트 전체 (git 커밋) |
| 5 | `~/.claude/settings.json` | 나, 모든 프로젝트 |

> ⚠️ **단, `deny` 규칙은 이 순서를 따르지 않는다.**
> 어느 층에서든 차단되면 다른 층에서 허용할 수 없다. 사용자 설정의 `deny`가 프로젝트 설정의 `allow`를 막고, 관리형 설정의 `deny`는 `--allowedTools`로도 뚫을 수 없다.

<br>

## 권한 모드

| 모드 | 묻지 않고 실행되는 것 | 적합한 상황 |
| --- | --- | --- |
| `default` (Manual) | 읽기만 | 모든 동작을 직접 검토, 민감한 작업 |
| `acceptEdits` | 읽기 + 파일 편집 + `mkdir`·`mv` 같은 기본 파일 명령 | 내가 보면서 코드를 반복 수정할 때 |
| `plan` | 읽기 + 읽기 전용 명령 | 바꾸기 전에 코드베이스 탐색 |
| `auto` | 전부 (백그라운드 안전 검사를 거침) | 긴 작업, 승인 피로 줄이기 |
| `dontAsk` | 사전 승인된 것만. 물어볼 상황은 `전부 거부` | 잠긴 CI, 스크립트 |
| `bypassPermissions` | 전부 | `격리된 컨테이너·VM에서만` |

- CLI에서는 `default`가 **Manual**로 표시됨 (설정값은 `default`, `manual`도 별칭으로 허용)
- `auto` 모드는 사람 대신 `분류 모델`이 동작을 검토함
  - 범위 확대, 알 수 없는 인프라 접근, 적대적 콘텐츠에 유도된 동작을 차단하고 나머지는 통과시킴
- `dontAsk`는 `acceptEdits`와 성격이 반대임
  - 물어볼 상황이 오면 승인이 아니라 `거부`로 처리 → 무인 실행에서 예측 가능성이 높음

### 전환과 기본값

```bash
# 세션 중 전환
Shift+Tab                      # 모드 순환

# 시작할 때 지정
claude --permission-mode plan
claude --permission-mode default
```

```json
// ~/.claude/settings.json — 모든 세션을 Manual로 시작
{
  "permissions": {
    "defaultMode": "default"
  }
}
```

- 프로젝트 `.claude/settings.json`에 넣으면 그 프로젝트만 적용
- 단, `auto`와 `bypassPermissions`는 프로젝트·로컬 설정에서 지정해도 적용되지 않음 (안전장치)

## 권한 규칙

### 세 종류와 평가 순서

| 규칙 | 동작 |
| --- | --- |
| `allow` | 승인 없이 실행 |
| `ask` | 매번 확인 |
| `deny` | 차단 |

```
deny  →  ask  →  allow
```

- 이 순서로 평가되고 `첫 번째 일치가 결과를 결정함`
- `규칙의 구체성은 순서를 바꾸지 않음`
  - `deny: Bash(aws *)`가 있으면 `allow: Bash(aws s3 ls)`가 있어도 차단됨
  - **allow로 deny의 예외를 만들 수 없다**
  - `ask`와 `allow` 사이도 같음 — 일치하는 `ask`가 있으면 더 구체적인 `allow`가 있어도 물어봄

### 규칙 문법

```
Tool              # 그 도구의 모든 사용
Tool(specifier)   # 특정 사용만
```

| 규칙 | 의미 |
| --- | --- |
| `Bash` | 모든 Bash 명령 |
| `Bash(npm run build)` | 정확히 이 명령만 |
| `Read(./.env)` | 현재 디렉토리의 `.env` 읽기 |
| `WebFetch(domain:example.com)` | 해당 도메인 요청 |

- `deny`에서 `도구 이름만` 쓰면 그 도구가 `Claude의 컨텍스트에서 제거됨` — Claude는 그 도구의 존재를 모름
- 반면 `Bash(rm *)`처럼 범위를 지정하면 도구는 남아있고 `일치하는 호출만 차단됨`

### 와일드카드 — 가장 흔한 실수

```json
{
  "permissions": {
    "allow": [
      "Bash(npm run *)",
      "Bash(git commit *)"
    ],
    "deny": [
      "Bash(git push *)"
    ]
  }
}
```

> ⚠️ **`*`는 반드시 서브커맨드 뒤에 둬야 한다.**
> Claude Code는 `첫 `*` 이전까지를 그대로` 매칭한다. 따라서 `*`의 위치가 규칙의 범위를 결정한다.

| 규칙 | 매칭됨 | 안 됨 |
| --- | --- | --- |
| `Bash(git log *)` | `git log --oneline` | `git push` |
| `Bash(git *)` | **모든 git 명령** (`git push`까지) | — |
| `Bash(git * main)` | `git merge main`, **`git push origin main`** | `git log` |
| `Bash(npm run *)` | `npm run build`, `npm run` | `npm install` |
| `Bash(ls *)` | `ls -la`, `ls` | `lsof` |
| `Bash(ls*)` | `ls -la`, **`lsof`** | — |

- `Bash(git * main)`처럼 `*`가 서브커맨드 자리에 오면 `git push`까지 허용됨 — 의도와 정반대
  - 이런 규칙은 시작 시 경고가 표시됨
- 끝에 붙은 `*` 앞의 `공백도 규칙의 일부`
  - `Bash(ls *)`는 `lsof`에 안 걸리지만 `Bash(ls*)`는 걸림
- `Bash(ls:*)`는 `Bash(ls *)`와 같음 (끝에서만 유효)

### 추가 매칭 방식

- `도구 이름 와일드카드` — `deny`/`ask`에서만
  - `"mcp__*"` → 모든 MCP 도구 차단
  - `allow`에서는 `mcp__<서버>__*` 형태로 서버를 명시해야 함
- `입력 파라미터 매칭` — `deny`/`ask`에서만

```json
{
  "permissions": {
    "ask": [
      "Agent(model:opus)",
      "Bash(run_in_background:true)"
    ]
  }
}
```

- 주의: 도구의 `주 내용 필드`는 이 방식으로 매칭할 수 없음
  - Bash의 `command`, Read의 `file_path`, WebFetch의 `url` 등
  - `Bash(command:rm *)`는 복합 명령으로 우회 가능하므로 무시되고 경고가 뜸 → `Bash(rm *)`로 써야 함

### 관리

```bash
/permissions    # 규칙 목록과 각 규칙의 출처 파일 확인
```

- Claude가 작업 중에도 열 수 있고, 추가·삭제가 `다음 도구 호출부터 적용됨`

<br>

## 작업 디렉토리

- 기본적으로 `실행한 디렉토리`의 파일에만 접근 가능

```bash
claude --add-dir ../shared-lib   # 시작할 때
/add-dir ../shared-lib           # 세션 중
```

```json
{
  "permissions": {
    "additionalDirectories": ["../shared-lib"]
  }
}
```

- 추가된 디렉토리는 원래 작업 디렉토리와 `같은 권한 규칙`을 따름
- 작업 디렉토리 밖 읽기를 아예 막으려면 `permissions.blockReadsOutsideWorkingDirectories`

<br>

## 어떤 모드도 자동 승인하지 않는 것

`bypassPermissions`에서도 자동 승인되지 않는 동작들이 있다.

- 명시적 `ask` 규칙에 일치하는 도구
- 사용자 상호작용이 필요한 도구 (`AskUserQuestion` 등)
- `중요 경로를 대상으로 하는 rm·rmdir` — 어떤 allow 규칙으로도 승인되지 않음
- 세션 간 메시징 안전장치

또한 `보호 경로`(`.git`, `.claude` 등)에 대한 쓰기는 `bypassPermissions` 외에는 자동 승인되지 않는다.

<br>

## 실전 설정 예시

### 로컬 개발 — 프롬프트 줄이되 위험한 건 막기

```json
// .claude/settings.json (팀 공유)
{
  "permissions": {
    "allow": [
      "Bash(npm run *)",
      "Bash(git status)",
      "Bash(git diff *)",
      "Bash(git log *)",
      "Bash(git add *)",
      "Bash(git commit *)"
    ],
    "ask": [
      "Bash(git push *)"
    ],
    "deny": [
      "Bash(rm -rf *)",
      "Read(./.env)",
      "Read(./.env.*)",
      "Bash(aws *)"
    ]
  }
}
```

- `.env` 읽기를 `deny`로 막는 건 중요함 — 비밀값이 컨텍스트에 들어가면 모델로 전송됨
- 배포·인프라 명령(`aws`, `kubectl`, `terraform`)은 기본 차단해두는 편이 안전

### CI — 정확한 허용 목록만

```bash
claude -p "테스트를 실행하고 실패를 고쳐줘" \
  --permission-mode dontAsk \
  --allowedTools "Bash(npm test)" "Read" "Edit"
```

- `dontAsk`이므로 목록에 없는 동작은 `물어보지 않고 거부됨`
- 무인 실행에서 가장 예측 가능한 조합

### 조직 차원 — 되돌릴 수 없는 모드 막기

```json
// 관리형 설정
{
  "permissions": {
    "disableBypassPermissionsMode": "disable",
    "deny": [
      "Bash(terraform apply *)",
      "Bash(kubectl delete *)"
    ]
  }
}
```

- 관리형 설정의 `deny`는 어떤 하위 설정이나 CLI 인자로도 뚫리지 않음

<br>

## 워크스페이스 신뢰

- 프로젝트 `.claude/settings.json`의 `allow` 규칙과 `additionalDirectories`는 `권한을 부여`하는 설정임
  - 그래서 그 폴더를 `신뢰하겠다고 확인한 뒤에야` 적용됨
  - 확인 대화창이 어떤 규칙·디렉토리를 부여하는지 보여줌
- `deny`와 `ask`는 제한만 하므로 신뢰 확인과 무관하게 즉시 적용됨
- 남이 만든 저장소에서 `claude -p`를 돌릴 때 주의
  - 신뢰 대화창이 뜨지 않으므로, 프로젝트의 훅과 `env` 블록이 그대로 실행될 수 있음
  - `--setting-sources user`로 프로젝트 설정을 아예 읽지 않게 하거나, `--bare`로 훅·스킬·MCP를 모두 끌 수 있음

<br>

## 흔한 함정

| 함정 | 결과 |
| --- | --- |
| `CLAUDE.md`에 "위험한 명령 금지"만 적음 | 강제되지 않음. 규칙이나 훅으로 써야 함 |
| `allow`로 `deny`의 예외를 만들려 함 | 안 됨. deny가 먼저 평가됨 |
| `Bash(git * main)` 같은 규칙 | `git push`까지 허용됨 |
| `Bash(command:rm *)`로 차단 시도 | 무시됨. `Bash(rm *)`로 써야 함 |
| `.env` 읽기를 막지 않음 | 비밀값이 컨텍스트에 들어가 모델로 전송됨 |
| `bypassPermissions`를 로컬에서 사용 | 보호 경로 쓰기까지 허용됨. 컨테이너에서만 쓸 것 |
| 프로젝트 `allow`가 적용 안 됨 | 워크스페이스 신뢰를 아직 수락하지 않은 상태 |

<br>

## 체크리스트

```
□ .env 등 비밀 파일을 deny에 넣었는지
□ 인프라·배포 명령(aws, kubectl, terraform)을 deny 또는 ask에 두었는지
□ allow 규칙의 * 가 서브커맨드 뒤에 있는지
□ git push를 ask로 둘지 결정했는지
□ 팀 공유할 규칙은 .claude/settings.json, 개인 규칙은 settings.local.json
□ settings.local.json이 .gitignore에 있는지
□ 반드시 매번 실행돼야 하는 검사는 훅으로 옮겼는지
□ bypassPermissions는 격리 환경에서만 쓰는지
□ /permissions로 실제 적용된 규칙과 출처를 확인했는지
```
