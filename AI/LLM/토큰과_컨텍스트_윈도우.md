# 토큰과 컨텍스트 윈도우

- LLM을 다루면서 `비용`, `레이턴시`, `실패`가 모두 이 두 개념에서 나옴
  - 토큰: 과금과 길이의 단위
  - 컨텍스트 윈도우: 한 요청에 담을 수 있는 총량의 상한
- 백엔드 개발자 입장에서는 `예산 관리 문제`에 가까움
  - 한정된 예산(컨텍스트 윈도우)에 무엇을 넣고 무엇을 버릴지 결정하는 설계

<br>

## 토큰 (Token)

- 모델이 텍스트를 다루는 `최소 단위`
- 단어도 아니고 글자도 아닌, `자주 등장하는 문자 조각` (subword)
  - 대표적으로 `BPE`(Byte Pair Encoding) 계열 알고리즘으로 어휘를 구성
  - 자주 쓰이는 단어는 토큰 하나, 드문 단어는 여러 조각으로 쪼개짐

```
"tokenization"  →  ["token", "ization"]        2 토큰
"the"           →  ["the"]                     1 토큰
"antidisestablishmentarianism"
                →  ["anti", "dis", "establish", "ment", "arian", "ism"]
```

### 왜 단어 단위가 아닌가

- `단어 단위`로 하면 어휘 사전이 무한히 커지고, 사전에 없는 단어(신조어, 오타, 고유명사)를 처리할 수 없음
- `글자 단위`로 하면 사전은 작아지지만 시퀀스가 너무 길어져 비효율적
- subword는 그 사이의 타협
  - 사전 크기를 고정하면서, 모르는 단어도 조각으로 분해해 표현 가능

### 한국어는 토큰을 더 많이 쓴다

- 토크나이저는 대부분 `영어 텍스트에 최적화`되어 학습됨
  - 영어는 자주 쓰는 단어가 통째로 토큰 하나인 경우가 많음
  - 한국어는 조사·어미 변화가 많아 한 단어가 여러 조각으로 쪼개지기 쉬움
- 같은 의미의 문장이라도 `한국어가 영어보다 토큰을 더 소비`함
  - 같은 컨텍스트 윈도우에 담을 수 있는 내용이 상대적으로 적음
  - 같은 분량을 처리할 때 비용도 더 나옴
- 정확한 비율은 모델과 토크나이저 버전에 따라 다르므로, `실제 데이터로 측정`해야 함

<br>

## 토큰 수 세기

- 토큰 수는 `추측하거나 글자 수로 환산하지 말고` API로 측정
  - 공식 토큰 카운팅 엔드포인트가 있음 (`/v1/messages/count_tokens`)
  - 실제 요청과 같은 `system`, `tools`, `messages`를 넘기면 그 요청의 입력 토큰 수를 알려줌

```
POST /v1/messages/count_tokens
{
  "model": "claude-opus-5",
  "system": "...",
  "tools": [ ... ],
  "messages": [ ... ]
}
```

- `다른 모델의 토크나이저로 센 값은 맞지 않음`
  - 모델 제공자마다, 심지어 같은 제공자의 모델 세대마다 토크나이저가 다름
  - OpenAI용 `tiktoken`으로 Claude의 토큰을 세면 어긋남
- 도구 정의와 시스템 프롬프트도 `전부 입력 토큰`임
  - 도구를 수십 개 붙이면 질문을 보내기 전부터 수천 토큰이 소모됨
  - 요청 본문만 보고 토큰을 가늠하면 실제보다 한참 적게 추정하게 됨

### 실제 사용량은 응답에서 확인

- 응답의 `usage` 필드에 실제 과금된 토큰이 들어 있음
  - `input_tokens`, `output_tokens`
  - `cache_creation_input_tokens`, `cache_read_input_tokens` (캐싱을 쓰는 경우)
- 이 값을 로그로 남겨두지 않으면 나중에 비용 분석이 불가능함
  - 요청 단위로 적재해 두면 어떤 기능이 토큰을 먹는지 추적할 수 있음

<br>

## 컨텍스트 윈도우 (Context Window)

- 한 요청에서 모델이 한 번에 볼 수 있는 `토큰의 총량`
- `입력과 출력이 같은 예산을 나눠 씀`

```
┌─────────────────── 컨텍스트 윈도우 ───────────────────┐
│ 도구 정의 │ system │ 대화 기록 │ 이번 질문 │  출력 공간  │
└───────────────── 입력 ─────────────────┴─────────────┘
```

- 입력이 커지면 `출력에 쓸 수 있는 공간이 줄어듦`
  - 입력으로 윈도우를 거의 채우면 응답이 짧게 잘림
- 출력에는 입력과 별개로 `자체 상한`도 있음
  - 컨텍스트 윈도우가 1M이라도 한 번에 생성 가능한 출력은 그보다 훨씬 작음
- 모델별 실제 수치는 `Models API`로 조회할 수 있음
  - `max_input_tokens`: 컨텍스트 윈도우
  - `max_tokens`: 출력 상한
  - 코드에 숫자를 하드코딩하지 말고 조회하거나 설정으로 빼는 편이 안전함

### max_tokens와의 관계

- `max_tokens`는 `이번 응답에서 생성할 출력 토큰의 상한`
  - 컨텍스트 윈도우와는 다른 값
  - 모델은 이 값을 알지 못함. 도달하면 문장 중간에서 그냥 잘림
- 너무 낮게 잡으면 응답이 잘려 재시도가 필요해짐
  - 분류처럼 짧은 출력이 확실한 경우를 빼면 넉넉하게 주는 편이 나음
- 값을 크게 주면 `스트리밍`이 사실상 필수
  - 응답 완성까지 기다리다 HTTP 타임아웃에 걸릴 수 있음

## 컨텍스트가 길어지면 생기는 문제

### 1. 비용이 대화 길이에 비례해 늘어난다

- LLM API는 상태를 기억하지 않으므로 `매 요청마다 전체 대화 기록을 다시 전송`
- 턴이 쌓이면 매 요청의 입력 토큰이 누적됨
  - 10턴째 요청은 1턴째보다 훨씬 비쌈
  - 대화가 길어질수록 `요청당 비용이 우상향`

### 2. 길다고 품질이 좋아지지 않는다

- 윈도우가 크다고 관련 없는 문맥까지 넣으면 오히려 품질이 떨어짐
  - 모델이 집중해야 할 정보가 희석됨
- `필요한 것만 골라 넣는 것`이 핵심
  - 이 선별 작업 자체가 `컨텍스트 엔지니어링`의 영역

### 3. 레이턴시가 늘어난다

- 입력이 길어지면 첫 토큰까지의 시간이 늘어남
- 다만 전체 응답 시간을 지배하는 쪽은 보통 `출력 길이`

<br>

## 컨텍스트 예산 관리 전략

대화나 작업이 윈도우를 넘길 때 쓸 수 있는 선택지들이다. 아래로 갈수록 구현 비용이 크다.

### 1. 잘라내기 (Truncation)

- 오래된 메시지를 앞에서부터 버림
- 가장 단순하지만 `버린 내용은 완전히 사라짐`
- 시스템 프롬프트와 최근 N턴만 유지하는 형태가 일반적

### 2. 요약 (Compaction)

- 오래된 대화를 `요약으로 치환`해 토큰을 줄임
- 직접 구현할 수도 있고, 서버 측 기능을 쓸 수도 있음
  - 임계치(예: 15만 토큰)에 도달하면 자동으로 이전 문맥을 요약
  - 이 경우 응답으로 돌아온 `content 전체를 다음 요청에 그대로 돌려줘야` 압축 상태가 유지됨. 텍스트만 뽑아 붙이면 조용히 깨짐

### 3. 컨텍스트 편집 (Context Editing)

- 요약이 아니라 `특정 블록을 제거`하는 방식
  - 오래된 도구 실행 결과 제거
  - 추론 블록 제거
- 에이전트 루프에서 도구 결과가 윈도우를 잡아먹을 때 효과적
  - 요약과 달리 내용을 압축하지 않고 통째로 비움

### 4. 외부로 내보내기

- 긴 내용을 윈도우 안에 들고 있지 않고 `파일이나 저장소에 두고 필요할 때만 읽어옴`
  - 진행 상황은 `progress.txt`, 작업 상태는 `tests.json` 같은 구조화된 파일에 기록
  - git 로그 자체를 상태 추적 수단으로 쓰는 방법도 있음
- 컨텍스트가 초기화되어도 파일에서 상태를 복원할 수 있어, `여러 컨텍스트 윈도우에 걸친 긴 작업`이 가능해짐

### 5. 애초에 필요한 것만 검색해 넣기

- 전체 문서를 넣는 대신 질문과 관련된 부분만 검색해서 주입
  - `RAG`의 기본 발상
- 윈도우가 커져도 이 접근이 여전히 유효한 이유는 2번 문제(길면 품질이 떨어짐) 때문

<br>

## 참고로 알아둘 것

- 일부 모델은 `남은 컨텍스트를 스스로 인식`함
  - 남은 예산을 보고 작업 범위를 조절하거나, 마무리를 서두르기도 함
  - 하네스가 자동으로 압축해 주는 환경이라면, 그 사실을 프롬프트에 알려줘야 모델이 작업을 조기에 중단하지 않음
- 캐시된 입력 토큰은 `훨씬 저렴하게` 과금됨
  - 긴 고정 접두사(시스템 프롬프트, 도구 정의, 참조 문서)가 있다면 캐싱이 가장 효과적인 비용 절감 수단
  - 배치 방법은 [프롬프트 엔지니어링](https://github.com/lcomment/development-recipes/blob/main/AI/Paradigm/프롬프트_엔지니어링.md)의 캐시 친화적 설계 참고
