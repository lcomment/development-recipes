# Function Calling과 도구 사용

- 모델이 외부 함수를 `호출하도록` 하는 메커니즘
- 가장 흔한 오해부터 바로잡을 필요가 있음

> **모델은 함수를 실행하지 않는다.** 모델이 하는 일은 `어떤 함수를 어떤 인자로 호출해야 하는지 알려주는 것`뿐이다. 실제 실행은 애플리케이션이 한다.

- 이 구분이 중요한 이유
  - 모델에게 실행 권한이 없으므로, `무엇을 실행할지는 전적으로 애플리케이션의 결정`
  - 따라서 권한 검증과 안전장치를 넣을 자리가 명확히 존재함

<br>

## 왜 필요한가

LLM 자체로는 할 수 없는 일들이 있다.

| 모델의 한계 | 도구로 해결 |
| --- | --- |
| 학습 시점 이후의 사실을 모름 | 검색, API 조회 |
| 사내·개인 데이터를 모름 | DB 질의, 파일 읽기 |
| 정확한 계산에 약함 | 계산기, 코드 실행 |
| 외부 상태를 바꿀 수 없음 | 메일 발송, 티켓 생성 |
| 현재 시각을 모름 | 시스템 시간 조회 |

- 도구가 없으면 모델은 `모르는 것을 그럴듯하게 꾸며냄`
- 도구가 있으면 `모른다는 것을 인지하고 조회`하게 됨

<br>

## 동작 흐름

```
1. 애플리케이션 → 모델
   "질문 + 사용 가능한 도구 목록(이름, 설명, 입력 스키마)"

2. 모델 → 애플리케이션
   "get_weather를 {location: "Seoul"}로 호출해줘"   ← stop_reason: tool_use

3. 애플리케이션
   실제로 get_weather("Seoul") 실행              ← 여기서 권한 검증

4. 애플리케이션 → 모델
   "결과: 기온 18도, 흐림"

5. 모델 → 애플리케이션
   "서울은 현재 18도이고 흐립니다"                 ← stop_reason: end_turn
```

- 2번에서 모델이 멈추고 `stop_reason`이 `tool_use`가 됨
- 4번에서 결과를 돌려주면 모델이 이어서 답변을 생성
- 이 왕복이 여러 번 반복되면 `에이전트 루프`가 됨
  - 루프 설계는 [AI 에이전트란?](https://github.com/lcomment/development-recipes/blob/main/AI/Agent/ai_에이전트.md) 참고

<br>

## 도구 정의

도구는 보통 세 가지로 정의한다.

```json
{
  "name": "get_weather",
  "description": "특정 지역의 현재 날씨를 조회한다. 예보가 아니라 현재 시점의 관측값을 반환한다.",
  "input_schema": {
    "type": "object",
    "properties": {
      "location": {
        "type": "string",
        "description": "도시명 또는 '위도,경도' 형식의 좌표"
      },
      "units": {
        "type": "string",
        "enum": ["metric", "imperial"],
        "description": "온도 단위. 기본값 metric"
      }
    },
    "required": ["location"]
  }
}
```

| 필드 | 역할 |
| --- | --- |
| `name` | 고유 식별자. 모델이 이 값으로 도구를 지정 |
| `description` | 무엇을 하는 도구이고 `언제 쓰는지` |
| `input_schema` | JSON Schema로 정의한 입력 파라미터 |

### description이 가장 중요하다

- 모델이 도구를 고르는 `유일한 근거`가 설명문임
- 설명이 부실하면 도구를 안 쓰거나, 엉뚱한 도구를 씀

| 나쁜 설명 | 좋은 설명 |
| --- | --- |
| `날씨 조회` | `특정 지역의 현재 날씨를 조회한다. 예보가 아니라 현재 관측값이다.` |
| `사용자 정보` | `사용자 ID로 프로필을 조회한다. 이메일로는 조회할 수 없다.` |
| `검색` | `제품 카탈로그를 키워드로 검색한다. 주문 내역 검색에는 쓸 수 없다.` |

- `무엇을 못 하는지`를 적어주면 오용이 크게 줄어듦
- 파라미터 설명에도 형식·단위·기본값을 명시

### 좋은 도구 세트의 조건

- `기능이 겹치지 않음`
  - 어떤 상황에서 무엇을 쓸지 의심의 여지가 없어야 함
  - 가장 흔한 실패는 "기능은 많지만 경계가 모호한 도구 세트"
- `반환값은 양이 아니라 질`
  - 불필요한 필드는 그대로 입력 토큰 낭비
  - 모델이 판단에 쓰지 않는 메타데이터는 제거
- `이름이 자기 설명적`
  - `calculate`보다 `calculator_arithmetic`처럼 범위가 드러나는 이름

<br>

## 스키마를 강제하기

- 모델이 스키마를 지키지 않는 인자를 만들 수 있음
- 도구 정의에 `strict` 옵션을 켜면 `인자가 스키마를 반드시 만족하도록` 보장됨

```json
{
  "name": "get_weather",
  "description": "...",
  "strict": true,
  "input_schema": {
    "type": "object",
    "properties": { "location": { "type": "string" } },
    "required": ["location"],
    "additionalProperties": false
  }
}
```

- `strict`는 도구 정의의 `최상위 필드`임 (`tool_choice`가 아님)
- 스키마에 `additionalProperties: false`와 `required`가 있어야 함
- 분류 작업이라면 유효한 라벨을 `enum`으로 가진 도구가 깔끔함

<br>

## 병렬 호출

최신 모델은 서로 의존하지 않는 도구를 `한 번에 여러 개` 호출한다.

```
assistant 메시지
├─ tool_use: read_file("a.ts")
├─ tool_use: read_file("b.ts")
└─ tool_use: read_file("c.ts")
```

### 결과는 반드시 한 메시지에 모아서 반환

```
✅ user 메시지 하나에 tool_result 3개
❌ user 메시지 3개에 tool_result 각 1개
```

- 쪼개서 보내면 `모델이 병렬 호출을 하지 않도록 학습됨`
  - 다음 턴부터 하나씩 순차 호출하게 되어 느려짐
- 이건 성능 문제이자 `조용히 나빠지는` 종류의 버그라 알아채기 어려움

### 실패한 도구도 결과를 돌려준다

- 에러가 났다고 `tool_result`를 생략하면 모델이 혼란에 빠짐
- 에러 표시와 함께 반드시 반환

```json
{
  "type": "tool_result",
  "tool_use_id": "toolu_...",
  "is_error": true,
  "content": "해당 지역을 찾을 수 없습니다"
}
```

- 모델은 이 결과를 보고 `다른 인자로 재시도`하거나 사용자에게 상황을 설명함

<br>

## 도구 호출 제어

- `tool_choice`로 모델의 선택지를 제한할 수 있음

| 설정 | 동작 |
| --- | --- |
| `auto` | 모델이 판단 (기본값) |
| `any` | 반드시 도구 중 하나를 호출 |
| `tool` | 지정한 도구를 호출 |
| `none` | 도구를 호출하지 않음 |

- 단, `강제 호출(any·tool)이 일부 최신 모델에서는 제거되어 400 에러를 반환함`
  - 대안: `auto` + 프롬프트에 도구명을 명시하는 지시
  - JSON을 받기 위해 강제 호출을 썼던 경우라면 `구조화된 출력`으로 대체

### 도구를 안 쓰려고 할 때

- 최신 모델은 지시를 문자 그대로 따르는 경향이 강함

| 도구를 안 씀 | 도구를 씀 |
| --- | --- |
| `이 함수를 개선할 방법을 제안해줄래?` | `이 함수의 성능을 개선하도록 수정해라` |
| `어떻게 하면 좋을지 알려줘` | `인증 플로우를 수정해라` |

- "제안해줘"라고 하면 정말 제안만 하고 끝남
- 반대로 구형 모델용으로 써둔 `반드시 이 도구를 써야 한다` 같은 강한 어투는 최신 모델에서 `과발동`을 유발함
  - [프롬프트 엔지니어링](https://github.com/lcomment/development-recipes/blob/main/AI/Paradigm/프롬프트_엔지니어링.md)의 안티패턴 참고

<br>

## 도구가 많아질 때

### 도구 정의는 전부 입력 토큰이다

- 질문을 보내기 전부터 도구 정의만으로 수천 토큰이 소모될 수 있음
- MCP 서버를 여러 개 붙이면 특히 빠르게 늘어남
- 관련: [토큰과 컨텍스트 윈도우](https://github.com/lcomment/development-recipes/blob/main/AI/LLM/토큰과_컨텍스트_윈도우.md)

### 캐싱과 순서

- 도구 정의는 요청 조립 순서상 `가장 앞`에 옴
  - 도구 목록이 바뀌면 `그 뒤 전체 캐시가 무효화됨`
- 따라서 도구 목록은 `항상 같은 순서로 직렬화`해야 함
  - 조건에 따라 도구를 넣고 빼면 캐시 히트율이 떨어짐
- 관련: [프롬프트 캐싱](https://github.com/lcomment/development-recipes/blob/main/AI/LLM/프롬프트_캐싱.md)

### 도구 검색 (지연 로딩)

- 도구가 수십 개를 넘으면 전부 올리는 대신 `필요할 때 검색`하게 할 수 있음
- 도구에 `지연 로딩` 표시를 하고, 검색 도구를 통해 찾아 쓰게 함
- 주의: `전부 지연 로딩으로 두면 에러`
  - 검색 도구 자신과 최소 하나의 도구는 즉시 로딩 상태여야 함

<br>

## 서버측 도구

- 직접 구현하지 않고 `제공자 인프라에서 실행되는` 도구들
  - 웹 검색, 웹 페치, 코드 실행 등
- 선언만 하면 되고 `실행 루프를 만들 필요가 없음`
  - 결과가 같은 응답의 콘텐츠 블록으로 돌아옴

| | 직접 구현 도구 | 서버측 도구 |
| --- | --- | --- |
| 실행 위치 | 내 서버 | 제공자 인프라 |
| 루프 | 직접 구현 | 불필요 |
| 통제 | 완전 | 제한적 |
| 적합 | 사내 시스템 연동 | 검색, 코드 실행 |

- 주의: 서버측 도구의 에러는 `예외로 던져지지 않음`
  - HTTP 200으로 오고, 결과 블록 안에 에러 객체가 담겨 있음
  - 성공 시 리스트, 실패 시 객체인 경우가 있어 타입을 먼저 확인해야 함

<br>

## 구조화된 출력과의 관계

- 둘 다 "모델에게 정해진 형식을 받는다"는 점에서 비슷하지만 목적이 다름

| | Function Calling | 구조화된 출력 |
| --- | --- | --- |
| 목적 | `동작을 수행`하게 함 | `응답 형식`을 고정 |
| 결과 | 도구를 실행하고 루프가 이어짐 | 그대로 응답이 끝남 |
| 쓰는 경우 | 외부 조회·변경이 필요 | JSON으로 파싱할 응답이 필요 |

- JSON만 받고 싶은 거라면 도구를 억지로 만들지 말고 `구조화된 출력`을 쓰는 편이 간단함

<br>

## 흔한 함정

### 1. 도구 인자를 문자열 매칭으로 읽기

- 모델·버전에 따라 `JSON 이스케이핑 방식이 달라질 수 있음`
  - 유니코드 이스케이프, 슬래시 이스케이프 등
- 반드시 `JSON 파서로` 역직렬화할 것. 직렬화된 문자열에 정규식을 걸면 언젠가 깨짐

### 2. 결과를 쪼개 보내기

- 위에서 다룬 병렬 호출 문제. 조용히 성능이 나빠짐

### 3. 실패한 도구 결과 누락

- 모델이 호출 결과를 기다리는 상태로 남음

### 4. 도구 설명이 겹침

- `search_user`와 `find_user`가 둘 다 있으면 모델이 매번 다른 선택을 함
- 하나로 합치거나 경계를 설명문에 명시

### 5. 되돌릴 수 없는 작업에 게이트가 없음

- 모델이 `결제`, `메일 발송`, `삭제`를 호출할 수 있다면 실행 전에 승인 단계가 필요
- 특히 `연쇄 실행` 중에는 사람이 보고 있지 않다고 가정해야 함

<br>

## 보안

- `모델의 출력은 사용자 입력과 같은 신뢰 수준`으로 취급해야 함
  - 도구 호출 인자도 모델이 생성한 값임
  - 그 값을 검증 없이 SQL이나 셸 명령에 넣으면 안 됨
- 권한 검증은 `도구를 실행하는 애플리케이션 쪽에서` 해야 함
  - 모델에게 "이 사용자는 관리자가 아니니 호출하지 마"라고 지시하는 것은 방어가 아님
  - 프롬프트 인젝션으로 우회됨
- 도구가 반환한 데이터에도 `지시가 심겨 있을 수 있음`
  - DB 행, 웹 페이지, 파일 내용은 모두 공격자가 통제할 수 있는 영역
  - 결과를 데이터로 명확히 표시하고, 그 안의 문장을 지시로 해석하지 않도록 지시
