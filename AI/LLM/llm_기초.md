# LLM이란?

- `LLM`(Large Language Model, 대규모 언어 모델)
  - 방대한 텍스트로 사전 학습된, `다음 토큰을 예측`하는 모델
  - 질문에 답하는 것처럼 보이지만, 실제로는 `주어진 문맥 다음에 올 확률이 가장 높은 토큰`을 반복해서 이어붙이는 것
- 대부분 `Transformer` 아키텍처 기반
  - Self-Attention으로 문맥 내 토큰 간의 관계를 계산
  - 순차 처리(RNN)와 달리 `병렬 처리`가 가능해 대규모 학습이 가능해짐

## 동작 과정

1. `토큰화 (Tokenization)`
   - 입력 텍스트를 모델이 다루는 최소 단위인 `토큰`으로 분할
   - 토큰은 단어가 아니라 `자주 등장하는 문자 조각` (subword)
2. `임베딩 (Embedding)`
   - 각 토큰을 고차원 벡터로 변환
3. `Attention 연산`
   - 문맥 내 어떤 토큰에 얼마나 집중할지 가중치를 계산
4. `확률 분포 출력`
   - 다음에 올 토큰 후보 전체에 대한 확률 분포를 생성
5. `샘플링`
   - 확률 분포에서 토큰 하나를 선택하고, 그 토큰을 입력 뒤에 붙여 1번부터 반복
   - 종료 조건(최대 토큰 수 도달, 종료 토큰 생성)을 만나면 멈춤

## 백엔드 개발자가 알아야 할 LLM의 특성

### 1. Stateless

- LLM API는 `대화 상태를 기억하지 않음`
  - 서버가 세션을 들고 있는 게 아니라, 매 요청마다 `전체 대화 기록을 다시 전송`해야 함
- 대화가 길어질수록 매 요청의 입력 토큰이 누적되어 늘어남
  - 비용과 레이턴시가 `대화 길이에 비례해 증가`
  - 오래된 대화는 요약(Compaction)하거나 잘라내는 전략이 필요

```json
{
  "model": "claude-opus-5",
  "max_tokens": 16000,
  "system": "너는 주문 처리를 돕는 어시스턴트다.",
  "messages": [
    { "role": "user", "content": "1번 주문 상태 알려줘" },
    { "role": "assistant", "content": "1번 주문은 배송 중입니다." },
    { "role": "user", "content": "그럼 언제 도착해?" }
  ]
}
```

- `system`: 모델의 역할과 규칙을 정의하는 영역. 대화 내내 고정되는 성격
- `messages`: `user`와 `assistant`가 번갈아 쌓이는 대화 기록
- `max_tokens`: 응답으로 생성할 `출력 토큰의 상한`. 도달하면 문장 중간에 잘림

### 2. 확률적 (Non-deterministic)

- 같은 입력에 대해 `항상 같은 출력이 나오지 않음`
  - 샘플링 과정에 무작위성이 있기 때문
- 단위 테스트의 `assertEquals` 방식이 통하지 않음
  - 출력 형식(JSON 스키마 등)은 제약을 걸어 고정하고, 내용의 품질은 `평가(Eval)`로 측정하는 접근이 필요

### 3. 컨텍스트 윈도우 제한

- 한 요청에 담을 수 있는 `입력 + 출력 토큰의 총량`에 상한이 있음
- 모델 체급에 따라 크게 다름
  - 상위 모델은 `1M 토큰`(한국어 기준 수십만 자) 규모, 경량 모델은 `200K 토큰` 수준
  - 구체적인 수치는 모델이 자주 바뀌므로 [공식 모델 문서](https://platform.claude.com/docs/en/models/overview)에서 확인하는 편이 안전함
- 출력 토큰은 입력과 `별도의 상한`이 있음
  - 컨텍스트 윈도우가 1M이라도 한 번에 생성할 수 있는 출력은 그보다 훨씬 작음
- 컨텍스트 윈도우가 크다고 아무거나 다 넣으면 안 됨
  - 입력 토큰은 그대로 `비용`이고 `레이턴시`
  - 관련 없는 문맥이 많아지면 오히려 응답 품질이 떨어짐

### 4. 지식 컷오프와 환각 (Hallucination)

- 모델은 `학습 시점까지의 지식`만 가지고 있음
  - 학습 이후의 사실, 사내 데이터, 실시간 데이터는 모름
  - 해결: 필요한 정보를 `프롬프트에 직접 넣어주거나`(RAG), `도구를 호출해 가져오게` 함
- 모르는 것을 모른다고 하지 않고 `그럴듯하게 꾸며내는 경우`가 있음
  - 확률적으로 가장 자연스러운 토큰을 이어붙이는 구조이기 때문
  - 사실 여부가 중요한 영역에서는 출처를 함께 반환하게 하거나 검증 단계를 두어야 함

## 입력 토큰과 출력 토큰

- 과금과 성능 모두 `입력`과 `출력`을 분리해서 봐야 함

|  | 입력 토큰 | 출력 토큰 |
| --- | --- | --- |
| 생성 방식 | 한 번에 병렬 처리 | 한 토큰씩 순차 생성 |
| 단가 | 상대적으로 저렴 | 입력의 5배 수준 |
| 레이턴시 영향 | 비교적 작음 | `지배적` |

- 응답이 느린 주된 원인은 입력이 길어서가 아니라 `출력이 길어서`인 경우가 많음
  - 출력 길이를 줄이는 것(불필요한 설명 제거, 형식 제약)이 가장 직접적인 레이턴시 개선
- 토큰 수는 추측하지 말고 `토큰 카운팅 API`로 측정해야 함
  - 모델마다 토크나이저가 다르므로 다른 모델용 토크나이저로 센 값은 맞지 않음

## 호출 설계 시 고려사항

- `스트리밍`
  - 출력이 길거나 `max_tokens`가 큰 요청은 스트리밍으로 받아야 함
  - 응답 완성까지 기다리면 HTTP 타임아웃에 걸릴 수 있음
  - 사용자 체감 레이턴시(첫 토큰까지의 시간)도 크게 개선됨
- `타임아웃과 재시도`
  - LLM 호출은 수 초에서 수 분까지 걸릴 수 있어, 일반 API 기준의 타임아웃(수 초)으로는 부족
  - 429(rate limit), 5xx는 재시도 대상이지만 400은 아님. 구분해서 처리해야 함
  - 재시도는 비용이 다시 발생하므로 무제한 재시도는 위험
- `프롬프트 캐싱`
  - 요청 간 반복되는 긴 접두사(시스템 프롬프트, 도구 정의, 참조 문서)를 캐싱해 비용과 레이턴시를 줄임
  - `접두사 일치` 방식이라, 고정 내용을 앞에 두고 가변 내용을 뒤에 배치하는 설계가 필요
- `비동기 처리`
  - 실시간 응답이 필요 없는 대량 작업은 배치 API를 쓰면 비용을 절반 수준으로 줄일 수 있음
  - 사용자 요청 흐름에서 분리해 큐로 넘기는 구조가 적합
- `샘플링 파라미터는 더 이상 주요 제어 수단이 아님`
  - 예전에는 `temperature`, `top_p`, `top_k`로 출력의 무작위성을 조절했음
  - 최신 모델에서는 제거되거나 무시되는 추세
    - Claude 최신 모델은 이 파라미터들을 지정하면 400 에러, Gemini도 최신 버전에서는 제거를 권고
  - 대신 `effort` 설정으로 추론 깊이와 토큰 사용량을 조절함
    - 모델이 스스로 추론량을 정하는 `적응형 추론(adaptive thinking)`이 기본이 되었기 때문
