# 프롬프트 캐싱

- 요청 간 반복되는 `프롬프트 접두사`를 서버에 캐싱해 재사용하는 기능
- 긴 시스템 프롬프트, 도구 정의, 참조 문서를 매 요청 다시 보낼 때 효과가 큼
  - 비용과 레이턴시를 동시에 줄임
- LLM 비용 최적화에서 `가장 먼저 시도할 수단`
  - 품질을 깎지 않고 비용만 줄이는 몇 안 되는 방법

<br>

## 동작 방식

- 프롬프트의 `접두사(prefix)`를 캐싱하는 방식
  - 요청의 앞부분이 이전 요청과 완전히 같으면 그 부분을 캐시에서 읽어옴
  - `1바이트라도 다르면 그 지점 이후 전체가 캐시 미스`
- 요청이 조립되는 순서

```
tools  →  system  →  messages
```

- 이 순서대로 `변하지 않는 것 → 변하는 것`을 배치해야 함

```
[도구 정의]        고정
[system]          고정
[참조 문서]        고정
--------------------------- 캐시 경계 (breakpoint)
[대화 기록]        누적
[이번 질문]        가변
```

<br>

## 사용법

### 자동 캐싱

- 요청 최상위에 `cache_control`을 넘기면 알아서 마지막 캐시 가능 블록에 경계를 잡아줌
- 대화가 늘어나면 경계도 따라 이동함
- 세밀한 제어가 필요 없는 다중 턴 대화에 적합

```json
{
  "model": "claude-opus-5",
  "max_tokens": 1024,
  "cache_control": { "type": "ephemeral" },
  "system": "...",
  "messages": [ ... ]
}
```

### 명시적 breakpoint

- 블록 단위로 `cache_control`을 직접 지정
- 어디까지 캐싱할지 정확히 통제해야 할 때 사용

```json
{
  "system": [
    {
      "type": "text",
      "text": "고정된 긴 지침 ...",
      "cache_control": { "type": "ephemeral" }
    }
  ],
  "messages": [
    { "role": "user", "content": "이번 질문" }
  ]
}
```

- breakpoint는 요청당 `최대 4개`
  - 자동 캐싱을 함께 쓰면 명시적 3개 + 자동 1개
- 각 breakpoint는 최대 `20개 블록`까지만 거슬러 올라가 캐시를 찾음
  - 연속된 `tool_use`/`tool_result`는 각각 1개로 계산
  - 턴이 많이 쌓이면 이전 캐시가 이 범위를 벗어나므로 breakpoint를 추가해야 함

<br>

## TTL과 비용

### TTL

| 설정 | 유지 시간 |
| --- | --- |
| `{"type": "ephemeral"}` | 5분 (기본) |
| `{"type": "ephemeral", "ttl": "1h"}` | 1시간 |

- 캐시 히트가 발생하면 TTL이 갱신됨
  - 요청이 꾸준히 들어오는 구간이라면 5분으로도 계속 유지됨
- 요청 간격이 5분보다 긴 워크플로우라면 1시간 캐시를 고려

### 비용 배수

| 구분 | 기본 입력 대비 |
| --- | --- |
| 캐시 쓰기 (5분) | `1.25배` |
| 캐시 쓰기 (1시간) | `2배` |
| 캐시 읽기 | `0.1배` 이하 (최신 모델은 더 저렴) |

- 쓰기에 25% 더 내고, 이후 읽기에서 90% 이상 절약하는 구조
  - 같은 접두사를 `두 번 이상` 쓰면 이득
  - 한 번만 쓰고 버리는 요청에 캐싱을 걸면 오히려 손해
- 구체적인 단가는 모델마다 다르므로 [공식 가격 문서](https://platform.claude.com/docs/en/about-claude/pricing) 확인

<br>

## 최소 캐시 가능 토큰

- 접두사가 `일정 길이 이상`이어야 캐시됨
- 모델에 따라 `512 ~ 4,096 토큰`

| 최소 토큰 | 모델 (예시) |
| --- | --- |
| 512 | Opus 5.5, Opus 5, Sonnet 5.5, Haiku 5.5 |
| 1,024 | Opus 4.8, Sonnet 5, Sonnet 4.6 |
| 2,048 | Opus 4.7 |
| 4,096 | Opus 4.6, Haiku 4.5 |

- **미만이면 에러 없이 조용히 캐시되지 않음**
  - 캐싱을 걸었는데 효과가 없다면 접두사 길이를 먼저 확인해야 함
  - 이 "조용한 실패"가 캐싱 디버깅에서 가장 흔한 함정

<br>

## 캐시가 깨지는 조건

| 변경한 것 | 무효화 범위 |
| --- | --- |
| 도구 정의 (내용·순서·구성) | `전체` |
| `tool_choice` | system 이후 |
| 이미지 추가/제거 | messages |
| thinking / effort 설정 | 모델에 따라 system 이후 |
| 속도 설정(fast mode) 전환 | system 이후 |

- 코드에서 흔히 저지르는 무효화 원인
  - 시스템 프롬프트에 `현재 시각`이나 요청 ID를 넣음
  - JSON 직렬화 시 `키 순서가 매번 달라짐` (정렬해서 직렬화해야 함)
  - 조건에 따라 도구 목록을 다르게 구성함
  - 요청마다 모델을 바꿈 (`캐시는 모델별로 분리됨`)
- 대화 중간에 시스템 지시를 추가해야 한다면, 최상위 `system`을 수정하지 말 것
  - 최상위를 고치면 그 뒤 전체가 무효화됨
  - 일부 모델은 `messages` 배열에 `role: "system"` 메시지를 덧붙이는 방식을 지원해, 캐시된 접두사를 유지할 수 있음

<br>

## 효과 확인하기

- 응답의 `usage`로 실제 캐시 동작을 확인

```json
{
  "usage": {
    "input_tokens": 50,
    "cache_read_input_tokens": 100000,
    "cache_creation_input_tokens": 5120,
    "output_tokens": 503
  }
}
```

| 필드 | 의미 |
| --- | --- |
| `cache_read_input_tokens` | 캐시에서 읽어온 토큰 (저렴하게 과금) |
| `cache_creation_input_tokens` | 새로 캐시에 기록한 토큰 |
| `input_tokens` | breakpoint 이후의 캐시되지 않은 토큰 |

```
총 입력 토큰 = cache_read + cache_creation + input_tokens
```

- `반복 요청에서 cache_read_input_tokens가 계속 0이면` 어딘가에서 접두사가 깨지고 있는 것
  - 이 값을 모니터링 지표로 잡아두면 무효화를 조기에 발견할 수 있음

<br>

## 캐싱 가능한 영역

- 캐시 가능
  - 도구 정의
  - 시스템 메시지
  - 텍스트 메시지
  - 이미지와 문서
  - 도구 호출(`tool_use`)과 결과(`tool_result`)
- 캐시 불가
  - 추론(thinking) 블록에 직접 `cache_control` 지정 — 단, 다른 콘텐츠와 함께 캐시됨
  - 블록의 일부분 (최상위 블록 단위만 가능)
  - 빈 텍스트 블록

<br>

## 실전 팁

### 캐시 프리워밍

- 첫 요청은 캐시 쓰기라 느림. 트래픽이 들어오기 전에 미리 캐시를 채워둘 수 있음
- `max_tokens: 0`으로 요청하면 응답을 생성하지 않고 캐시만 기록

### TTL 혼합

- 변경 빈도가 다른 영역에 다른 TTL을 줄 수 있음
  - 거의 안 바뀌는 대형 지침 → `1h`
  - 하루 단위로 갱신되는 컨텍스트 → 기본 5분

### 안티패턴

- `매번 변하는 내용 끝에 breakpoint를 둠`
  - 캐시 쓰기만 반복되고 히트는 영원히 발생하지 않음
  - 쓰기 비용(1.25배)만 계속 더 내는 최악의 형태
- breakpoint는 반드시 `항상 동일한 내용의 끝`에 둬야 함
