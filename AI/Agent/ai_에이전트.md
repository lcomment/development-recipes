# AI 에이전트란?

- `LLM이 도구를 사용해 스스로 일을 진행하는 구조`
- 프롬프트 한 번에 답을 받는 것이 아니라, 모델이 `판단 → 도구 실행 → 결과 확인 → 다시 판단`을 반복함
- 컨텍스트 엔지니어링이 `판단 재료`를 최적화하는 일이라면, 에이전트는 `판단 이후의 실행`까지 모델에게 맡기는 것

<br>

## 워크플로우와 에이전트

같은 "여러 단계를 거치는 작업"이라도 `제어권을 누가 갖는지`에 따라 성격이 완전히 다르다.

| | 워크플로우 | 에이전트 |
| --- | --- | --- |
| 흐름 제어 | `코드`가 결정 | `모델`이 결정 |
| 단계 | 미리 정해짐 | 실행 중에 결정됨 |
| 예측 가능성 | 높음 | 낮음 |
| 디버깅 | 쉬움 | 어려움 |
| 적합한 작업 | 절차가 명확한 파이프라인 | 사전에 명세하기 어려운 탐색적 작업 |

```
[워크플로우]  요약 → 분류 → 알림     ← 순서가 코드에 박혀 있음

[에이전트]    "이 버그를 고쳐줘"
              → 파일을 검색할까? 로그를 볼까? 테스트를 돌려볼까?
              → 모델이 매 턴 스스로 결정
```

- 둘 중 하나를 고르는 문제가 아니라 `단계(tier)`로 봐야 함

| 티어 | 적합한 경우 |
| --- | --- |
| 단일 호출 | 분류, 요약, 추출, 질의응답 |
| 워크플로우 | 절차가 명확한 다단계 파이프라인 |
| 에이전트 | 사전에 전부 명세할 수 없는 열린 작업 |

- `가장 단순한 티어부터` 시작하는 것이 원칙
  - 에이전트는 비용과 레이턴시가 크고 디버깅이 어려움
  - 단일 호출로 되는 일을 에이전트로 만들면 모든 면에서 손해

<br>

## 에이전트 루프

- 에이전트의 본질은 `반복문` 하나

```
1. 모델에게 요청 (대화 기록 + 도구 목록)
2. 응답 확인
   - 도구 호출을 요청했다면 → 도구 실행 → 결과를 대화에 추가 → 1번으로
   - 끝났다고 하면 → 종료
```

- 의사 코드

```
while response.stop_reason == "tool_use":
    results = execute(response.tool_calls)
    messages.append(response)
    messages.append(results)
    response = call_model(messages, tools)
```

- 이 루프를 `직접 구현`할 수도 있고, SDK가 제공하는 러너에 맡길 수도 있음
  - 직접 구현: 루프 전체를 통제하고 싶을 때
  - SDK 러너: 도구 함수만 작성하고 루프는 맡김. 턴별 훅으로 승인·로깅·재시도를 끼울 수 있음

<br>

## 구성 요소

### 1. 도구 (Tools)

- 모델이 외부와 상호작용하는 유일한 통로
- 도구 정의의 품질이 에이전트 품질을 좌우함
  - 기능이 겹치는 도구를 만들지 않음
  - 어떤 상황에서 무엇을 쓸지 `의심의 여지가 없어야` 함
  - 반환값은 양이 아니라 질 — 불필요한 필드는 토큰 낭비

### 2. 루프와 중단 조건

- `무한 루프 방지`가 설계 필수 요소
  - 최대 턴 수 제한
  - 비용 상한
  - 같은 도구를 같은 인자로 반복 호출하면 중단
- 모델에게 `예산을 알려주는` 방법도 있음
  - 작업 예산(task budget)을 주면 모델이 스스로 속도를 조절하고 마무리를 준비함
  - 응답 토큰 상한(`max_tokens`)과는 다름. 후자는 모델이 알지 못하는 강제 절단

### 3. 컨텍스트 관리

- 턴이 쌓이면 도구 실행 결과가 컨텍스트를 빠르게 잡아먹음
- 압축, 도구 결과 제거, 외부 파일 저장 등으로 관리해야 함
  - 자세한 전략은 [컨텍스트 엔지니어링](https://github.com/lcomment/development-recipes/blob/main/AI/Paradigm/컨텍스트_엔지니어링.md) 참고

### 4. 병렬 실행

- 서로 의존하지 않는 도구 호출은 `동시에` 실행해야 함
- 결과는 `하나의 메시지에 모아서` 반환
  - 여러 메시지로 쪼개 보내면 모델이 병렬 호출을 하지 않도록 학습됨
- 실패한 도구도 결과를 돌려줘야 함 (에러 표시와 함께). 누락시키면 모델이 혼란에 빠짐

<br>

## 에이전트를 만들어야 하는가

도입 전에 네 가지를 확인한다. 하나라도 `아니오`면 더 단순한 티어가 맞다.

| 기준 | 질문 |
| --- | --- |
| `복잡도` | 다단계이고, 사전에 전부 명세하기 어려운가? |
| `가치` | 높은 비용과 레이턴시를 감당할 만한 결과인가? |
| `실현성` | 모델이 이 종류의 작업을 실제로 해낼 수 있는가? |
| `실패 비용` | 틀렸을 때 잡아내고 되돌릴 수 있는가? (테스트, 리뷰, 롤백) |

- 특히 `실패 비용`이 중요함
  - 테스트로 검증 가능한 코드 수정은 에이전트에 적합
  - 돌이킬 수 없는 외부 전송이나 결제는 적합하지 않음

<br>

## 운영상 위험

| 위험 | 대응 |
| --- | --- |
| 비용 폭증 | 턴 수·토큰 상한, 사용량 로깅과 알림 |
| 되돌릴 수 없는 작업 | 파괴적 동작은 승인 게이트를 두고, 권한을 서버에서 검증 |
| 무한 루프 | 중단 조건, 동일 호출 반복 감지 |
| 환각 누적 | 검증 도구 제공, 확인하지 않은 내용을 단정하지 않도록 지시 |
| 디버깅 불가 | 매 턴의 요청·도구 호출·결과를 전부 추적 가능하게 로깅 |

- 로깅은 선택이 아니라 `필수`
  - 에이전트는 매 실행의 경로가 달라지므로, 기록이 없으면 왜 그렇게 동작했는지 영원히 알 수 없음
