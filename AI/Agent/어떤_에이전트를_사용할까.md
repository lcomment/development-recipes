# 어떤 에이전트를 사용할까?

- 코딩 에이전트를 직접 만들지 않고 `완성된 제품`을 쓰는 선택지
- 대표적으로 `Claude Code`, `Codex`, `Gemini CLI / Antigravity CLI`
- 세 도구 모두 터미널에서 코드베이스를 읽고 파일을 수정하고 명령을 실행함
  - 할 수 있는 일의 목록은 비슷하므로, `무엇이 다른지`를 보고 골라야 함

> ⚠️ **작성 기준: 2026년 10월**
> 이 영역은 변화가 매우 빠릅니다. 실제로 Gemini CLI는 2026년 5월 Antigravity CLI로의 전환이 발표되었고, 각 저장소의 README가 한동안 구버전 정보를 안내하기도 했습니다. 모델·가격·한도는 반드시 공식 문서에서 다시 확인하세요.

## AGENTS.md — 공통 표준

- 세 도구를 비교할 때 먼저 알아둘 것은 `프로젝트 컨텍스트 파일이 사실상 표준화되었다`는 점
- `AGENTS.md`는 코딩 에이전트를 위한 개방형 표준
  - "사람을 위한 README가 있다면, 에이전트를 위한 README"
  - 빌드 방법, 테스트 실행법, 코드 컨벤션 등을 적어둠
  - 6만 개 이상의 오픈소스 프로젝트, 30개 이상의 에이전트가 지원
- 도구를 바꿔도 `AGENTS.md는 그대로 쓸 수 있음`
  - Claude Code는 `CLAUDE.md`가 없으면 `AGENTS.md`를 읽음
  - 도구 종속성을 줄이려면 공통 내용은 `AGENTS.md`에, 도구별 특수 설정만 각자의 파일에 두는 방식이 깔끔함

## Claude Code

### 성격

- `확장 메커니즘과 실행 환경의 폭`이 가장 넓은 쪽
- 터미널에서 시작한 세션을 IDE, 데스크톱 앱, 웹, 모바일로 옮겨가며 이어갈 수 있음

### 확장 수단

| 수단 | 용도 |
| --- | --- |
| `CLAUDE.md` | 프로젝트 상시 컨텍스트 (자동 메모리도 누적) |
| 슬래시 커맨드 | 자주 쓰는 프롬프트를 명령으로 등록 |
| 스킬 | 반복 워크플로우를 패키징해 팀과 공유 |
| 서브에이전트 | 작업을 병렬로 쪼개 위임 |
| 훅(Hooks) | 파일 수정 후 포맷, 커밋 전 린트 등 자동 실행 |
| MCP | 외부 데이터·도구 연결 |
| Agent SDK | Claude Code의 하네스를 라이브러리로 사용 |

### 권한 모델

- `플랜 모드`: 읽기만 하고 수정하지 않음. 탐색·계획 전용
- `auto 모드`: 별도 분류 모델이 위험한 동작만 걸러내고 나머지는 승인 없이 진행
- `Manual 모드`: 파일 쓰기·명령 실행마다 승인
- 허용 목록(`/permissions`)과 OS 수준 샌드박싱(`/sandbox`)을 조합

### 강점

- `팀 단위로 워크플로우를 표준화`하기 좋음 — 스킬과 슬래시 커맨드를 저장소에 커밋해 공유
- `훅으로 결정론적 자동화`를 끼워넣을 수 있음. 모델의 판단에 맡기지 않고 강제되는 단계를 만들 수 있다는 점이 가장 큰 차별점
- 멀티파일 변경과 대규모 리팩터링에서 평이 좋음
- 파이프라인 친화적 — `tail -200 app.log | claude -p "..."` 형태로 Unix 도구와 조합
- CI 연동, 예약 실행, Slack 연동 등 자동화 표면이 넓음

### 약점

- `비공개 소스`. 내부 동작을 들여다보거나 포크해서 고칠 수 없음
- `무료 티어가 없음`. 구독이나 API 키가 필요
- 기능이 많아 `학습 곡선`이 있음
- 토큰 소비가 많은 편이라는 평가가 있음

## Codex

### 성격

- `ChatGPT 생태계에 통합`된 형태
- CLI뿐 아니라 ChatGPT 데스크톱·모바일·웹 앱에서 바로 작업을 지시할 수 있음
- 클라우드 환경에 작업을 위임하고 결과만 받아보는 흐름을 지원

### 권한 모델

샌드박스와 승인 정책이 `독립된 두 축`으로 분리되어 있다.

| 샌드박스 (`sandbox_mode`) | 동작 |
| --- | --- |
| `read-only` | 읽기만 가능 |
| `workspace-write` | 현재 저장소와 임시 디렉토리에만 쓰기 |
| `danger-full-access` | 어디든 쓰기 가능 |

| 승인 정책 (`approval_policy`) | 동작 |
| --- | --- |
| `untrusted` | 신뢰할 수 없는 동작마다 확인 |
| `on-request` | 경계를 넘을 때만 확인 |
| `never` | 확인하지 않음 |

- 기본값은 `workspace-write` + `on-request` 조합
  - 작업 디렉토리 안에서는 자유롭게 편집·실행하고, `밖으로 쓰거나 네트워크가 필요할 때만` 멈춰서 물어봄
- `--dangerously-bypass-approvals-and-sandbox`로 둘 다 해제 가능
- 세션 중간에 `/permissions`로 변경 가능
- OS 커널 수준 샌드박싱이라는 점이 강점으로 자주 언급됨

### 강점

- `코드 리뷰와 검증`이 가장 강하다는 평이 일관되게 나옴
- `CI 친화적` — GitHub 플로우와 PR 중심 작업에 붙이기 쉬움
- 토큰 효율이 좋다는 평가 (같은 작업에서 소비 토큰이 적음)
- 샌드박스/승인 축이 분리되어 있어 `무인 실행 정책을 정밀하게` 잡을 수 있음
- CLI가 Apache 2.0 오픈소스

### 약점

- 개발자 문서가 ChatGPT 학습 센터로 흡수되어 `레퍼런스 접근성이 떨어짐`
  - 샌드박스·승인 모드 같은 핵심 동작조차 공식 문서에서 바로 찾기 어려워, 커뮤니티 문서에 의존하게 되는 경우가 있음
- `멀티파일 구현`에서는 Claude Code보다 약하다는 평가가 많음
- 컨텍스트 윈도우에 대한 보고가 출처마다 엇갈림 — 큰 코드베이스에서 한계를 먼저 만난다는 지적이 있음

<br>

## Gemini CLI → Antigravity CLI

### 전환 중인 상태

- 2026년 5월, Google은 Gemini CLI를 `Antigravity CLI`로 전환한다고 발표
  - 터미널 도구가 나머지 워크플로우와 `통합된 백엔드`를 공유해야 한다는 판단
- `2026년 6월 18일`부터 개인 사용자(무료 Gemini Code Assist, Google AI Pro·Ultra) 대상 요청 처리가 중단됨
  - `과거의 넉넉한 무료 한도(분당 60회 / 일 1,000회)는 더 이상 유효하지 않음`
  - Standard·Enterprise 라이선스는 Gemini CLI를 계속 지원
- Antigravity CLI가 유지하는 기능: `Agent Skills`, `Hooks`, `Subagents`, `Extensions`(플러그인으로 개칭)
- Go로 다시 작성되어 더 빠르고, 여러 에이전트가 백그라운드에서 협력하는 비동기 워크플로우를 지원

> 이 전환이 비교에서 중요한 이유: `무료로 쓸 수 있다`가 Gemini CLI의 가장 큰 장점이었는데 그 전제가 사라졌다. 오래된 비교 글이 여전히 무료 한도를 장점으로 적고 있으므로 주의가 필요하다.

### 강점

- `Google Search 그라운딩이 내장`되어 최신 정보가 필요한 작업에 유리
  - 라이브러리 최신 버전, 최근 바뀐 API 같은 주제에서 체감됨
- Gemini CLI는 `Apache 2.0 오픈소스` — 동작을 읽고 고칠 수 있고, 사내 환경에 맞게 포크하는 선택지가 열려 있음
- 대용량 컨텍스트로 큰 코드베이스를 한 번에 밀어넣는 방식이 가능
- `신뢰 폴더(Trusted Folders)`, 샌드박싱, 체크포인트 기능 제공
- GitHub Action으로 PR 리뷰·이슈 트리아지, `@gemini-cli` 멘션 지원

### 약점

- `제품이 전환기에 있음`. 문서와 생태계가 Antigravity 쪽으로 이동 중이라 정보가 분산되어 있음
- `실행 환경이 터미널 중심`. IDE·데스크톱·모바일로 이어지는 흐름은 약함
- 멀티파일 구현 품질이 다른 둘보다 떨어진다는 평가가 있음
- 생태계와 서드파티 통합의 축적이 상대적으로 적음

<br>

## 기능 하나를 쳐낼 때 — 단계별 비교

기능 작업은 보통 `설계 → 구현 → 검증`을 거치고, 단계마다 요구하는 능력이 다르다.

| 단계 | 요구되는 능력 | 실패하면 |
| --- | --- | --- |
| 설계 | 코드베이스 탐색, 접근 방식 판단 | 엉뚱한 문제를 푼 코드가 나옴 |
| 구현 | 멀티파일 편집, 기존 패턴과의 일관성 | 동작은 하지만 코드베이스와 겉도는 코드 |
| 검증 | 자기 결과물을 객관적으로 평가 | 그럴듯하지만 엣지 케이스가 깨진 코드 |

### 근거의 두 종류

- `제품에 그 단계를 위한 기능이 있는가` — 공식 문서로 확인 가능하고 비교적 오래 유지됨
- `실제로 어느 쪽이 더 잘하는가` — 커뮤니티 실사용 평가. 유용하지만 `모델 세대가 바뀌면 뒤집힘`
- 아래는 둘을 구분해서 적는다

### 1. 설계 — 탐색하고 계획 세우기

- `Claude Code`
  - `플랜 모드`가 별도로 존재함. 파일을 읽고 질문에 답하지만 `수정은 하지 않는 모드`
  - 공식 권장 흐름이 `탐색 → 계획 → 구현 → 커밋` 4단계로 문서화되어 있음
  - 계획을 에디터로 열어 직접 수정한 뒤 진행시킬 수 있음
  - 큰 기능은 모델이 거꾸로 질문을 던지게 해서 `SPEC.md`를 먼저 만드는 패턴을 권장
  - 서브에이전트로 탐색을 별도 컨텍스트에 격리 — 조사 때문에 본 작업 컨텍스트가 오염되지 않음
- `Gemini CLI / Antigravity CLI`
  - `Google Search 그라운딩`이 내장되어, 처음 쓰는 라이브러리나 최근 바뀐 API를 조사하는 설계 단계에 유리
  - 큰 컨텍스트로 전체 구조를 한 번에 파악하는 방식이 가능
- `Codex`
  - 클라우드에 조사를 위임하고 결과만 받아보는 흐름. 자리를 비운 사이 진행시키기에 적합

> 설계 단계는 `되돌리기가 가장 싸다`. 여기에 시간을 쓰는 것이 구현을 다시 하는 것보다 항상 저렴하다.

### 2. 구현 — 코드를 쓰기

- 커뮤니티 평가가 가장 일관되게 갈리는 단계
  - `Claude Code가 멀티파일 구현에서 앞선다`는 평가가 반복적으로 나옴
  - 저장소를 읽고 계획을 세워 여러 파일에 걸친 변경을 끝까지 끌고 가는 데 손이 덜 간다는 것
  - 리팩터링, 마이그레이션, "코드베이스 전반에 걸쳐 적용" 류 작업에서 특히 그렇게 평가됨
- 반면 `병렬화 방식`은 도구마다 다르고, 이건 문서로 확인되는 차이

| | 병렬 작업 방식 |
| --- | --- |
| Claude Code | git worktree로 세션 분리, 서브에이전트, 대량 변경을 여러 에이전트로 분배 |
| Codex | 클라우드 환경에 작업 위임 |
| Antigravity CLI | 여러 에이전트의 백그라운드 비동기 협력 |

- 대규모 마이그레이션처럼 `같은 작업을 수백 개 파일에 반복`해야 한다면 비대화형 실행을 루프로 돌리는 방식이 핵심
  - 세 도구 모두 비대화형 실행(`-p`, `exec`)과 JSON 출력을 지원
  - 차이는 `무인 실행용 권한 장치`의 정밀도. Codex의 샌드박스/승인 2축 분리가 이 지점에서 유리

### 3. 검증 — 결과를 확인하기

가장 차이가 큰 단계이고, 가장 많이 생략되는 단계다.

- 핵심 원칙은 `작성자와 검증자를 분리하는 것`
  - 코드를 방금 쓴 세션은 자기 코드에 `편향됨`
  - 새 컨텍스트의 검증자는 추론 과정을 모르고 결과만 보므로 독립적으로 평가함
- `Codex`가 검증·리뷰에서 가장 강하다는 평가가 커뮤니티에서 일관되게 나옴
  - GitHub PR 중심 플로우에 붙이기 쉽고, 코드 리뷰와 자동 검토가 제품에 내장됨
  - 구현은 Claude Code, 리뷰는 Codex로 나누는 조합을 권하는 글이 여럿 있음
- `Claude Code`의 검증 수단 (문서화된 기능)
  - `/code-review` — 별도 컨텍스트의 서브에이전트가 diff를 검토. 여러 에이전트가 각각 다른 종류의 문제를 찾은 뒤 `거짓 양성을 걸러내는 검증 단계`를 거침
  - GitHub PR 자동 리뷰 — 심각도별 인라인 코멘트, `REVIEW.md`로 조정 (Team·Enterprise, 리뷰당 평균 $15~25)
  - `Stop 훅` — 검사가 통과할 때까지 턴이 끝나지 않게 `결정론적으로 막음`. 모델의 판단에 맡기지 않는 유일한 수단
  - Writer/Reviewer 세션 분리 패턴을 공식 문서가 권장
- `Antigravity CLI`
  - GitHub Action으로 PR 리뷰와 이슈 트리아지

> 다만 검증 단계에서 `도구 선택보다 더 중요한 것`이 있다. 모델이 읽을 수 있는 `pass/fail 신호`를 주는 것이다. 테스트 명령, 빌드 종료 코드, 린터, 스크린샷 비교 중 무엇이든 하나만 있으면 모델이 스스로 루프를 돌며 고친다. 이게 없으면 사람이 매번 검증 루프가 되고, 어떤 도구를 쓰든 결과는 비슷해진다.

### 단계별 요약

| 단계 | 상대적으로 유리한 쪽 | 근거 |
| --- | --- | --- |
| 설계 | `Claude Code` | 플랜 모드, 4단계 워크플로우 (문서) |
| 설계 (최신 기술 조사) | `Gemini / Antigravity CLI` | Search 그라운딩 (문서) |
| 구현 | `Claude Code` | 멀티파일 변경 완주력 (커뮤니티 평가) |
| 구현 (무인 대량 반복) | `Codex` | 샌드박스·승인 2축 분리 (문서) |
| 검증 | `Codex` | 리뷰 중심 설계, CI 친화성 (커뮤니티 평가) |
| 검증 (강제 게이트) | `Claude Code` | Stop 훅으로 결정론적 차단 (문서) |

### 하나만 고르지 않아도 된다

- 실사용 비교 글들이 공통적으로 내리는 결론은 `한 도구만 쓰지 않는다`는 것
  - 구현 → 리뷰 → 검증을 서로 다른 도구에 맡기는 조합
  - 작성자와 검증자를 분리한다는 원칙을 `도구 수준에서` 적용하는 셈
- `AGENTS.md`가 공통 표준이므로 이 조합이 실제로 가능함
  - 프로젝트 컨텍스트를 `AGENTS.md`에 모아두면 도구를 바꿔도 다시 설명할 필요가 없음

| 멀티파일 기능 구현 | `Claude Code` | 변경을 끝까지 끌고 가는 완주력 |
| 코드 리뷰·검증 | `Codex` | 리뷰 중심 설계, PR 플로우 친화 |
| 팀 워크플로우 표준화 | `Claude Code` | 스킬·슬래시 커맨드·훅을 저장소에 커밋해 공유 |
| 커밋 전 린트 등 강제 단계 | `Claude Code` | 훅으로 모델 판단과 무관하게 강제 |
| 무인 대량 마이그레이션 | `Codex` / `Claude Code` | 권한 모드 정밀도, worktree 분리 |
| 모바일에서 작업 위임 | `Codex` / `Claude Code` | ChatGPT 앱, 또는 웹·모바일 세션 |
| 최신 정보가 필요한 작업 | `Antigravity CLI` | Search 그라운딩 내장 |
| 사내 환경에 맞게 개조 | `Gemini CLI` / `Codex` | 오픈소스라 포크 가능 |
| 이미 쓰는 구독 활용 | 구독 중인 쪽 | 추가 비용 없음이 가장 큰 변수 |

## 고를 때 실제로 중요한 것

- `모델 성능 차이는 생각보다 빨리 수렴하고 빨리 뒤바뀜`
  - 벤치마크 몇 점 차이로 고르면 다음 분기에 판단이 뒤집힘
  - 공개 벤치마크 수치가 서로 가깝게 몰려 있어서, 의도적으로 수치를 제시하지 않는 비교 글도 있음
  - 오래 유지되는 차이는 `생태계`, `확장 방식`, `실행 환경`, `라이선스`, `권한 모델`
- `제품의 존속성`도 변수임
  - Gemini CLI의 Antigravity 전환처럼, 도구 자체가 바뀌거나 요금 정책이 뒤집힐 수 있음
  - 도구 종속을 줄여두면 이런 변화의 비용이 낮아짐
- `이미 쓰는 구독`이 가장 현실적인 기준인 경우가 많음
- 결국 `직접 써보는 것`이 가장 빠름
  - 비교 글의 평가는 작성 시점의 모델 기준이고, 내 코드베이스와 작업 성격에 따라 체감이 다름
