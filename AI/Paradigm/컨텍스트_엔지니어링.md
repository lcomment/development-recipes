# 컨텍스트 엔지니어링

- `모델에게 어떤 정보를 보여줄지 고르는 일`
- 토큰으로 표현되는 정보 집합 전체를 최적화해, 원하는 동작을 일관되게 얻어내는 작업
- 프롬프트 엔지니어링의 한계에서 등장
  - 지시문을 아무리 잘 써도, 모델이 모르는 외부 데이터를 알게 만들 수는 없음
  - 다중 턴 에이전트에서는 매 턴 컨텍스트가 변하므로, 한 번 잘 쓴 프롬프트로는 부족함

## 프롬프트 엔지니어링과의 차이

| | 프롬프트 엔지니어링 | 컨텍스트 엔지니어링 |
| --- | --- | --- |
| 범위 | 효과적인 지시문 작성 | 컨텍스트에 들어가는 모든 토큰의 관리 |
| 질문 | `무엇을 말할 것인가` | `어떤 정보를 포함할 것인가` |
| 성격 | 일회성(discrete) | 반복적(iterative) |
| 대상 | 단일 요청 | 다중 턴 에이전트 |

- 관리 대상에는 시스템 프롬프트, 도구 정의, 외부 데이터, 대화 기록이 모두 포함됨

<br>

## 전제: 컨텍스트는 유한한 자원이다

### Context Rot

- 컨텍스트가 길어질수록 `모델의 정보 회상 정확도가 떨어지는` 현상
- 두 가지 원인
  - `아키텍처 제약`: 트랜스포머는 n개 토큰에 대해 n² 쌍의 관계를 계산함. 컨텍스트가 커지면 각 토큰에 배분되는 `주의 예산(attention budget)`이 희석됨
  - `학습 분포`: 모델은 짧은 시퀀스로 더 많이 학습했기 때문에, 아주 긴 시퀀스를 다루는 전문화된 파라미터가 상대적으로 부족함
- 컨텍스트 윈도우가 1M으로 커져도 이 문제는 사라지지 않음
  - `넣을 수 있다`와 `넣어도 된다`는 다른 얘기

### 핵심 원칙

> 원하는 결과가 나올 확률을 극대화하는 `가장 작은 고신호(high-signal) 토큰 집합`을 찾는다.

- 컨텍스트 엔지니어링의 모든 기법이 이 한 문장으로 수렴함
- 더 넣는 게 아니라 `덜 넣으면서 더 정확하게` 넣는 작업

<br>

## 무엇을 어떻게 담을 것인가

### 1. 시스템 프롬프트 — 적정 고도(Altitude)를 찾는다

- 너무 낮으면: 모든 경우를 if-else로 하드코딩
  - 유지보수 비용이 폭증하고, 예상 못 한 상황에서 깨짐
- 너무 높으면: 모호한 고수준 지침만 제시
  - 암묵적 가정이 많아 모델이 의도를 해석하지 못함
- 적정 수준: `행동을 안내할 충분한 신호 + 판단의 유연성`

```
❌ 낮음  "주문번호가 1000번대면 A팀, 2000번대면 B팀, 3000번대면..."
✅ 적정  "주문 유형에 따라 담당 팀으로 분류한다. 판단이 어려우면 보류 상태로 남긴다."
❌ 높음  "주문을 적절히 처리한다"
```

- 구조는 섹션으로 분리
  - `<background_information>`, `<instructions>`, `## Tool guidance`, `## Output description` 등
  - XML 태그나 마크다운 헤더로 경계를 명확히
- `최소 정보 원칙`: 행동을 완전히 설명하되, 그 이상은 덜어냄

### 2. 도구 — 두 가지 효율을 본다

- `토큰 효율`
  - 도구가 반환하는 정보는 양이 아니라 질
  - 중복 필드, 쓰지 않는 메타데이터를 응답에서 제거
- `행동 유도 효율`
  - 기능이 겹치는 도구를 만들지 않음
  - 어떤 상황에서 어떤 도구를 쓸지 `의심의 여지가 없어야` 함
  - 입력 파라미터는 명확하고 짧게
- 가장 흔한 실패는 `기능은 많지만 경계가 모호한 도구 세트`
  - 에이전트가 도구 선택에서 헤매고, 잘못된 선택이 누적됨

### 3. 예시 — 규칙 나열보다 대표 사례

- 엣지 케이스를 전부 규칙으로 적는 것은 안티패턴
- `다양하고 대표성 있는 사례 몇 개`로 기대 행동을 보여주는 편이 효과적
  - 모델이 패턴을 인식해 일반화함

<br>

## Just-in-Time 컨텍스트

### 사전 로드 vs 런타임 검색

| | 사전 로드 | Just-in-Time |
| --- | --- | --- |
| 방식 | 관련 데이터를 미리 전부 넣음 | 식별자만 주고 필요할 때 도구로 가져옴 |
| 넣는 것 | 문서 본문 전체 | 파일 경로, 쿼리, URL |
| 장점 | 빠름 | 토큰 절약, 점진적 탐색 |
| 단점 | 컨텍스트 낭비, context rot | 런타임 탐색이 느림 |

- Just-in-Time의 이점
  - 전체 객체를 컨텍스트에 올리지 않아도 됨
  - `메타데이터 자체가 신호`가 됨 — 파일명, 폴더 계층, 타임스탬프가 탐색 방향을 알려줌
  - `점진적 발견(progressive disclosure)`: 각 단계에서 얻은 맥락이 다음 결정을 더 정확하게 만듦
- 예: 대규모 데이터를 전부 읽어오는 대신, 표적 쿼리를 만들어 결과를 파일로 저장하고 `head`/`tail`로 필요한 부분만 들여다봄

### 하이브리드가 현실적

- 속도가 중요한 일부 데이터는 `미리` 넣음 (프로젝트 규약, 자주 쓰는 설정)
- 나머지는 `glob`, `grep` 같은 탐색 도구로 `동적으로` 가져오게 함
- 작업 성격에 따라 자율성 수준을 조절

<br>

## 긴 작업을 위한 세 가지 기법

컨텍스트 윈도우 하나로 끝나지 않는 작업에서 쓰는 전략이다.

### 1. Compaction (압축)

- 윈도우 한계에 가까워지면 대화 기록을 `요약으로 치환`
- 보존할 것과 버릴 것
  - 보존: 아키텍처 결정, 미해결 버그, 구현 세부사항
  - 제거: 중복된 도구 실행 결과
- 압축된 요약 + 최근 파일 몇 개로 작업을 계속함
- 튜닝 순서는 `회수율(recall) 먼저, 정밀도(precision) 나중`
  - 먼저 중요한 걸 빠뜨리지 않게 만들고, 그다음 불필요한 걸 덜어냄
- 가장 안전한 경량 버전은 `도구 결과만 비우는 것`
  - 요약 과정에서 정보가 왜곡될 위험이 없음

### 2. Structured Note-taking (구조화된 메모)

- 컨텍스트 밖의 `영속 저장소에 메모를 남김`
  - 투두 리스트, `NOTES.md`, `progress.txt`
  - 상태 데이터는 JSON 같은 구조화된 형식, 진행 메모는 자유 서술
- 컨텍스트가 초기화돼도 메모를 다시 읽어 작업을 이어감
- `오버헤드가 가장 작은` 영속 메모리 방식
- git 로그 자체를 상태 추적 수단으로 쓰는 것도 같은 발상

### 3. Sub-agent (부에이전트)

- 하나의 에이전트가 모든 상태를 들고 있지 않고 역할을 나눔
  - 메인 에이전트: 고수준 계획과 조율
  - 부에이전트: 깨끗한 컨텍스트에서 초점화된 작업 수행
  - 부에이전트는 `압축된 요약만 반환` (보통 1,000~2,000 토큰)
- 탐색 과정의 방대한 컨텍스트가 `격리`되어 메인 컨텍스트를 오염시키지 않음

### 어떤 것을 쓸까

| 상황 | 기법 |
| --- | --- |
| 광범위한 상호작용이 길게 이어짐 | Compaction |
| 명확한 마일스톤이 있는 반복 개발 | Note-taking |
| 병렬 탐색이 유리한 조사·분석 | Sub-agent |

- 배타적이지 않으므로 조합해서 씀

<br>

## 백엔드 관점의 함의

- 컨텍스트 구성은 `런타임 로직`임
  - 프롬프트 템플릿 하나를 두고 끝나는 게 아니라, 매 요청 무엇을 넣을지 결정하는 코드가 필요
- 캐싱과 충돌하지 않게 설계해야 함
  - 동적으로 구성한다고 고정 영역의 순서까지 매번 바뀌면 캐시가 깨짐
  - `고정 블록은 고정 순서로, 가변 블록은 뒤에` 두는 원칙을 유지
- 무엇을 넣었는지 `로깅`해야 디버깅이 가능함
  - 응답이 이상할 때, 그 요청의 컨텍스트를 재구성할 수 없으면 원인을 찾을 수 없음

<br>

## 앞으로

- 모델이 똑똑해질수록 처방적인 엔지니어링은 덜 필요해짐
  - 에이전트에게 더 많은 자율성을 줄 수 있게 됨
- 다만 `컨텍스트를 소중한 유한 자원으로 다룬다`는 원칙 자체는 계속 유효함
